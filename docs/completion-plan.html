Sprint 1 · Context-aware AI

Weeks 2–3 · 12–25 Oct · 66% → 75%

Deliver the core promise of the proposal: recommendations driven by mood, preferences, location, weather and season, using our own trained models.

Objective 2RQ2RQ3FR-011NFR-001
  • Weather: add /api/weather on the backend (OpenWeather, key on the server, 30-minute cache).Rain or storms down-rank beaches, waterfalls and viewpoints and up-rank heritage sites. Show a weather chip on Home and on each itinerary day.
  • Retrain the recommender as a content-based model.The current model learns embeddings for synthetic user IDs, so it cannot score real users (cold start). New inputs: mood, eco preference, budget, month, weather, plus destination features (category, eco score, carbon index, popularity). Train on interactions.csv joined with users and destinations. Report precision@5 and NDCG against today's rule-based ranking.
  • Export the model to TensorFlow Lite and run it on the phone with react-native-fast-tflite over the 275 bundled destinations, so itineraries work offline as the design says.
  • Use the other two models.Eco scorer (random forest): batch-score all destinations and record the model version. Demand LSTM: export a monthly crowd forecast per destination and add a "fewer crowds" boost that favours under-visited places (supports Objective 6).
  • Log every generated itinerary to a recommendation_records collection (model version, inputs, results), as in design section 4.4.
  • For RQ3, assign each user a strategy (mood-based, location-based or seasonal) and log it with each recommendation.
Done when model metrics are written up, 95% of itineraries are generated in under 3 seconds, and itinerary generation works in airplane mode.

Sprint 2 · Preferences, offline travel and language

Weeks 4–5 · 26 Oct–8 Nov · 75% → 83%

Make the app usable without signal and in all three languages.

FR-002FR-010FR-012FR-020FR-021NFR-002NFR-006–008
  • Preferences form as designed: eco % and culture % sliders, budget, duration, mobility (walking only, low mobility). Saved on the phone and in Firestore, used by the model and pre-filled in the chatbot.

  • Offline route guidance.When an itinerary is saved online, fetch and store the route line for each leg. Offline, show the stored route on the downloaded map with live GPS, distance and direction to the next stop, and a re-centre when the traveller leaves the route.

Done when a full trip can be planned and followed in Sinhala and in Tamil, and a saved itinerary, map and route all work in airplane mode with tiles loading in under 1 second.

Sprint 3 · Safety, vendors and notifications

Weeks 6–7 · 9–22 Nov · 83% → 90%

Close the loops between tourists, vendors, guides, drivers and the tourism authority.

FR-001FR-040FR-041FR-050FR-051FR-060Seq. 4.2.5.2–3
  • SOS by SMS.Online: the backend sends an SMS to the emergency desk for every SOS through a gateway (Notify.lk, Dialog Ideamart or Twilio). Offline: the pre-filled SMS to the desk number stays, because Google Play does not allow silent SMS sending. Add an SMS log tab to the admin SOS monitor.
  • Emergency workflow in the SOS monitor: active → acknowledged → dispatched → resolved, recording which admin handled it, plus a "forward to authority" action with location and contact details.
  • Phone-number sign-up with an OTP check (Firebase phone auth).
  • Booking notifications: vendor or guide gets a push on a new request, the tourist gets a push on accept or reject, and after 15 minutes without a reply the tourist is shown other vendors.
  • Vendor verification in the admin portal: view uploaded NIC and certificate, reject with a reason, allow resubmission, suspend or ban later.
  • Reviews after visits: prompt after a completed booking or itinerary day. Add a GPS check-in at a destination (within 200 m) that writes visited_places and stamps the Eco Passport. Add saving places.
  • Privacy: split user profiles into a public part (name, photo, role) and a private part (email, phone) readable only by the owner, booking partners and staff.
Done when a booking goes request → accept → complete → review with notifications both ways, an SOS reaches the desk by SMS, and a rejected vendor can resubmit and be approved.

Sprint 4 · Research data collection

Weeks 8–9 · 23 Nov–6 Dec · 90% → 95%

Build what the evaluation chapter needs: consent, usage data and feedback, all visible to the team in the admin portal.

Objectives 4–6RQ1RQ3–RQ6Ethics

  • Usage events: recommendation shown, opened, saved, swapped, booked; event viewed and alert opened; vendor contacted; SOS used. Each event carries the user's strategy group from Sprint 1.

  • Replace the invented figures in Analytics.jsx and Reports.jsx with real aggregates.
Done when events from test users appear live on the research dashboard and the CSV export opens cleanly in Excel or Python.

Risks

What could slow us down

On-device AI needs a custom buildTensorFlow Lite does not run in Expo Go. Make the EAS development build in Phase 0 and use it from then on.
Model trained on synthetic dataState this openly in the thesis, compare against the rule-based baseline, and retrain on real interaction data collected in Sprint 4 if time allows.
Silent offline SMS is not allowed on Google PlayKeep the pre-filled SMS for offline use, send automatic SMS from the backend when online, and document the limitation.
API quotas and costPlaces, OpenWeather and the AI providers have limits. Cache on the backend, keep the rate limits, and use free tiers during the study.
Recruiting study participantsStart recruiting in Sprint 3 through campus, the original survey respondents and local guides. Book sessions before Sprint 5 starts.
Deadline earlier than week 13Cut stretch items first: offline tile provider switch, AR, extra admin reports. Never cut Phase 0, Sprint 4 or the usability study.

  • All SHOULD requirements done or justified in the thesis
  • Every NFR has a measured number in the test report
  • Rules tests, unit tests and E2E tests pass in CI
  • No hardcoded or random data left in any screen
  • No API keys inside the app bundle; old keys rotated
  • Full app usable in English, Sinhala and Tamil
  • Usability study done with SUS, timings and survey results
  • RQ1–RQ6 each answered with evidence
  • Thesis and design documents match the built system
  • Signed APK, hosted admin portal and live backend
  • Demo script, demo video and user guides ready
